** Before this is usable for anything real: **

1. Override every value under `secrets:` in values.yaml (jwtSecret,
   encryptionKey, anthropicApiKey, postgresPassword, postgresAppPassword,
   minioAccessKey, minioSecretKey) via a separate, non-committed values
   file or an external-secrets-operator ExternalSecret. The defaults are
   literal placeholders ("REPLACE_ME") that will fail app-level validation
   (AIVA_ENCRYPTION_KEY must decode to exactly 32 bytes -- see
   apps/api/app/settings.py) or simply aren't real secrets.

2. Set `image.registry` to wherever you push the five aiva-* images
   (api, ai-gateway, sandbox-runner, web-recruiter, web-candidate) --
   this chart does not build or push them itself.

3. For real AI inference rather than the deterministic mock backend, set
   `aiGateway.llmBackend: anthropic` and supply `secrets.anthropicApiKey`.

4. `postgres.enabled` / `redis.enabled` / `minio.enabled` default true and
   bundle a single-replica StatefulSet each with no backup/HA story of
   their own (see values.yaml's comment and docs/RUNBOOK.md's "Backup &
   restore: pending M12" line) -- fine for evaluation, not for anything
   you'd be upset to lose. Point `externalDatabaseUrl` /
   `externalRedisUrl` / external object storage at managed services
   instead and disable these for real production use.

5. `sandbox-runner`'s pod needs `CAP_SYS_ADMIN` to isolate candidate code
   execution at all (unshare --pid --net; see docs/DECISIONS.md's
   ADR-028) -- already wired into this chart's Deployment, but confirm
   your cluster's pod security admission policy actually permits it
   (a `restricted` Pod Security Standard profile will reject this
   capability outright; you need at least `baseline`, scoped to this one
   workload, not cluster-wide).

6. `ingress.enabled` is false by default and only routes web-recruiter
   (the staff console). web-candidate (the public candidate-facing app --
   a different trust boundary) deliberately needs its own explicit
   host/path decision, not a default.

** This chart's own verification status (see docs/DECISIONS.md's ADR-030): **
`helm lint` and `helm template` were both run and pass -- the chart is
structurally valid Helm/Kubernetes YAML. It has NOT been installed against
a real Kubernetes cluster (none was available in the environment this was
built in) -- rendering correctly is not the same claim as "deploys and
runs correctly." Treat this as a strong first draft to `helm install
--dry-run` against your own cluster and inspect before trusting it, not as
already-proven-in-production.
